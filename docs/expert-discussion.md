# 专家圆桌

内置 14 位研究专家及 Prompt 升级、自定义保护和公开参考见[专家研究视角](expert-personas.md)。专家数量增加不改变单次讨论人数限制或当前默认成员。

## 可视化讨论入口

`/expert-review` 位于主导航的投研助理之后。专家圆桌只用于专家协作：左侧为历史群聊，中央消息区独立滚动，顶部选择专家与协作模式，底部常驻输入框。用户、主持人、专家分别署名；专家意见与回应按原有 Markdown 章节或结构化字段阅读，默认展开首个章节，风险/反证章节以语义色标识。主持人最终总结直接显示在时间线内，并可打开宽版完整阅读窗口。追问在同一群聊中显示前几轮消息，不再只替换当前报告。公共证据、分工、质询与计票保持原展示方式。

专家发言不再截取 900 字符；只折叠章节，不删改内容。章节拆分保留嵌套标题、表格和代码围栏，窄屏表格可横向滚动。结构化意见复用报告中的观点/依据/反证视图；历史 JSON 的解析边界同[工作区报告](workspace-decision-reports.md)，不可解析部分不回退为正文代码块。完整原文在溯源入口保留。自评信心不从叙述文字推算，章节分组不意味着新增专家共识。

Roundtable expert opinions and responses now use expandable original sections instead of 900-character excerpts. The first section opens by default, with explicit risk/counterevidence styling. Host synthesis appears inline and in the wide reader using the same renderer. Nested headings, tables, source text, speaker order, response rounds, failed stages and voting semantics are retained. Structured outputs reuse the evidence view; malformed JSON stays in source disclosures with a warning. No new model calls or inferred scores are introduced. Revert the frontend and rebuild to roll back; no data migration is needed.

投研助理内的专家协作保留简洁运行状态和最终报告；专家圆桌则直接展开过程。流水线展示主持人分工、各专家成果及任务汇总；辩论展示公共证据、独立分析、质询回应及共识/分歧总结；投票展示专家报告、三位独立评审的投票对象和理由、服务端计票及主持人总结。主持人不参与投票。界面展示的是公开输出而非内部思考，按完整发言保存后轮询更新，不虚构逐字生成或中间状态。

## 入口与报告

- `/overview` 默认直接对话。输入框上方常驻“选择专家”和“协作方式”，选项列表向上展开，不跳转、不替换对话区、不清空输入。未选专家时为普通对话；协作选择 2–6 位专家，可以取消全部选择回到普通对话。执行中禁用配置修改，提供停止按钮，离开页面不会取消后台任务。
- 主 Agent 使用原有对话列表、输入框及消息渲染器，专家执行复用 `/expert-review` 的 `expert_review` Task/Run/Artifact 后端，而不是另一套聊天页面。独立专家讨论页仍可审阅专门报告。旧 `/overview?mode=discussion&run=<id>` 链接在原对话中加载报告追问上下文，不自动发起请求。
- 专家协作工作台保留讨论历史、议题输入和可读回复报告。专家模块仅选择具体成员和协作模式，不创建或选择命名小组；默认至多三位启用专家，协作至少需要两位。直接对话不受人数约束。
- 独立的“研究能力授权”区域可选择公共 Skill/工具/MCP/数据源与每位专家的授权子集；未自定义者继承公共能力，每位最多三个 Skill。这不是命名专家小组配置。
- 个股、选股、交易已结束且有成果的报告提供“邀请专家讨论这份报告”。后端根据 `sourceRunId` 读取真实存储成果，客户端不提供可冒充服务端报告的摘录。
- 发言以 Markdown 呈现在群消息中，完整报告通过卡片打开。“继续追问”默认继承当前查看记录的成员/能力，以 `parentDiscussionRunId` 引用前轮报告，新建 Run，不覆盖前轮成果。历史默认显示各分支最新轮，打开后追溯最多 100 轮父记录；读取失败或关联异常明确提示，不混入其他群聊。
- 原单专家咨询保留 `/expert-review?mode=single`，旧专家评审仍可阅读；专家讨论为全局一级导航。

### 对话内协作的保存边界

`config.chatSessionId` 可将专家运行关联到普通对话（仅字母、数字、下划线和短横线，最多 100 字符，禁止内部 `workspace-` 会话）。创建 Run 与用户消息在同一事务保存；终态与助手报告在同一事务保存，记录消息 ID 保证重复结束不重复发报告。失败、取消及服务重启也产生明确的终态消息。若用户已删除对应问题/会话，后台成果仍保存在运行账本，但不重新创建已删除会话。

每次运行冻结当前对话最近 12 条可见消息，每条最多 2000 字符，供专家理解上下文；裁剪可能遗漏更早细节，不能作为完整证据保证。最终报告进入普通消息历史，因此后续取消专家后仍可继续追问。新问题可以重新选择专家和方式，不强制继承上一轮参与者；独立讨论页的 `parentDiscussionRunId` 追问仍沿用冻结配置。

对话内专家继承本次会话的 Skill、工具、MCP、数据源授权。目录能力标记 `discussionChatBinding` 未就绪时禁止专家发送，但不影响普通聊天。恢复运行中的会话时显示实际配置；全新或已结束会话重新加载默认不自动选择专家，避免意外发起付费多专家请求。未提交的选择只保留于当前页面生命周期。

## 执行协议与权限

`Task.config.discussionProtocol = cross_response_v1` 仅适用于 `expert_review`。创建、更新及运行均验证协议、成员和权限；`crossExaminationRounds` 为 1 或 2；参与者 2 至 6 位，按 ID 去重。

1. 创建 Run 时，`discussionSnapshot` 冻结专家 Prompt/版本、每位成员的能力和 Skill 选择、工作区自定义 Skill 指令、关联成果摘录及来源 ID。内置 Skill 代码与工具实现仍使用部署版本，不声称冻结可执行代码。
2. 主持人不调用研究工具，只整理已有资料、协调和总结。具体研究由独立专家会话执行；不会将多个专家角色拼成单次模型调用。
3. 最多三位专家并发独立分析，独立会话和能力子集。开放议题不要求买卖评级。
4. 无工具权限的主持调用提取实质分歧，返回具名质询。只有成功发言的专家可被质询；每位每轮最多回应一个问题，读取同一份上一轮材料后补证或修正立场。无实质分歧提前总结；解析失败不是“没有分歧”。
5. 无工具权限的主持调用生成结论报告，保留少数意见、未解决问题和失败信息，不按票数决定结论。数据质量仍需人工核查。

专家能力通过 `config.expertCapabilities[expertId]` 保存，只允许 `skillIds/toolIds/mcpIds/dataSourceIds`，必须是任务授权子集；任务绑定仍必须通过工作区启用/可用性校验。不自动新增 MCP、不绕过数据源授权。讨论禁用内置整套个股/选股工作流工具，避免重复运行；其余授权工具可补证。交易议题不改变订单审批和执行边界。

新讨论默认最多 900 秒，旧单轮配置保留 600 秒预算；每次调用继承剩余预算与已配置的更短 Agent 超时，最多 6 个 Agent 步骤。预算耗尽或用户取消后不启动后续调用，保留已保存意见；正在执行的网络调用遵循底层取消/超时能力，不承诺毫秒级中断。用户刷新/离开页面不会取消 Run；服务重启仍按现有中断恢复规则结束未完成 Run，不支持阶段续算。

### 三种协作模式

`config.collaborationMode` 支持 `pipeline / debate / voting`；旧任务缺省为 `debate`。追问默认继承前轮冻结成员、授权和协作模式。群聊中点击“调整下轮配置”，显式提交 `config.reconfigureDiscussion: true`，才使用当前选择重新校验与冻结成员、授权和模式；前轮消息、配置和报告保持不变。该标志必须为布尔值，不能绕过人数、能力授权或来源成果校验。前端通过目录 `discussionReconfiguration` 标志确认后端支持，旧服务不允许提交调整。

群聊复用持久化父运行链，不新增命名专家小组、数据库表或环境变量。群消息显示全部已加载轮次，模型上下文仍沿用现有冻结证据摘要及截断上限，不代表每次模型请求都包含无限长聊天记录。运行中可输入草稿，但需当前轮结束后才能发出下一轮；切页不会取消执行。回滚新前后端代码和 Web 构建即可，旧历史仍可读取；已有显式调整配置的任务应使用支持该标志的版本执行。

- 流水线：主持人先输出有序分工，每位选中专家恰好负责一项；后端校验 ID、覆盖与重复。无效分工直接结束，不虚构替代计划。各专家依次执行自己的子任务，读取前序成果及失败缺口，主持人最后汇总。
- 辩论式：上述独立发言、提取分歧、交叉回应、总结流程；新讨论最多两轮，无实质分歧提前结束。
- 投票式：各专家独立产出完整报告，不读取彼此意见。随后三位独立评审 Agent 分别侧重证据、推理、任务覆盖和风险；各有独立会话，不是主持人或参赛专家，不读取其他评审票，也没有工具权限。每位投一票或弃权，服务端只接受候选整数 ID 与有效理由。至少两票才选出报告，平票、票数不足或候选不足均明确“未选出”。主持人不能改票；最终报告首先展示服务端计票选中的原报告，再附主持人总结。这里评的是报告质量，不是多数买卖方向。

新增 `DiscussionPlan / ExpertBallot / DiscussionVote` 成果保存分工、评审理由与计票。专家共享 Runtime 实现与已配置模型，但不共享会话上下文；不宣称使用不同基础模型。

新成果类型 `DiscussionEvidence`、`DiscussionQuestions`、`ExpertResponse` 与已有 `ExpertOpinion`、`ExpertReview` 同 Run 保存。失败专家及阶段写入报告载荷；有综合报告但部分阶段失败时业务结果为 `partial`，不掩盖为完整共识。

## 兼容、验证与回滚

能力目录追加 `discussionProtocols`、`discussionModes` 与 `discussionChatBinding`，客户端确认所需能力受支持才允许提交，避免连接旧后端时默默执行其他模式。旧任务没有新协议字段时保持旧行为；无需数据库迁移。旧小组数据/API 为历史兼容保留，但不再提供小组配置入口；默认试用直接绑定成员，旧选择在能力列表展开为具体专家。部署应等待旧任务结束再重启后端并发布对应 Web 构建。

确定性测试覆盖编排、真实交叉回应传递、无分歧提前结束、无效质询、权限子集、成员冻结、关联追问、部分失败、取消，以及前端创建、报告 Markdown、离页恢复与来源引用。模型事实质量和外部数据稳定性不由这些测试保证。

回滚代码与 Web 构建到上一版本即可，不删除任务或成果；旧客户端仍可从运行详情读取新增 Artifact。回滚前先停止接收新讨论并等待现有任务结束。
